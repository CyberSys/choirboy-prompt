# Безопасность и раскрытие

Рамка безопасности, очистка перед публикацией и правила ответственного
раскрытия. Документ описывает подход проекта к собственной безопасности.

---

## 1. Безопасность рабочего плагина

Проект публикуется как **плагин памяти для рабочих проектов**:

- проверки — на **своих** агентах, конфигурациях и файлах истории;
- без сторонних целей: чужие пользователи, их данные и их агенты
  не затрагиваются;
- изменения плагина проверяются локально до релиза.

Плагин не устанавливается в чужие системы без разрешения их владельца.
Публикуемые артефакты не содержат учётных данных и приватных данных пользователя.

---

## 2. Границы исследования

| Можно | Нельзя |
|---|---|
| Проверять плагин на своих агентах | Менять чужих агентов или пользовательские данные |
| Публиковать очищенную историю и документацию реализации | Публиковать учётные данные или рабочие инструменты восстановления чужих ключей |
| Направлять находки разработчикам | Эксплуатировать находки до исправления |
| Разбирать публично раскрытые инциденты | Выносить адреса жертв и полные консолидаторы |
| Давать разработчикам рекомендации по обнаружению | Публиковать PoC против действующих систем |

Эти границы — не декорация: они соответствуют `research/10` (аудит
чужих контрактов и ответственное раскрытие) и `research/09` (web3-
безопасность, энтропия ключей).

## 3. Чек-лист очистки перед публикацией

Плагин по своей природе несёт **личную память** — историю совместной
работы пары «человек + агент». Публичный репозиторий — это другое
пространство, чем локальная установка. Чек-лист:

### 3.1. Содержимое

Публикуется **очищенная** версия: история и исследования содержат рабочие
решения, но не содержат идентифицирующих деталей.

- [ ] `prompt.md`, `lore.md`, `user.md` — публикуются; проверены, что
      не содержат путей к приватным проектам и личных данных.
- [ ] `security-posture.md` — публикуется как часть контекста; проверена явная
      рамка авторизации и безопасности.
- [ ] `research/` — публикуется; проверено, что в нём нет имён
      конкретных NSFW/refusal-моделей, путей к файлам с адресами и полных
      адресов.
- [ ] `security-audit-runbook.md` — исполняемые команды аудита; безопасен,
      ссылается на `security-posture.md` — проверить связку.

### 3.2. Идентификация

- [ ] Нет упоминаний путей к приватным проектам (репозитории
      исследования слабой энтропии и т.п.).
- [ ] Нет полных адресов кошельков; только обезличенные префиксы
      (`bc1qnk…`), если они вообще нужны.
- [ ] Нет имён конкретных NSFW/refusal-моделей и LoRA, снимающих отказы;
      остаются функциональные роли («NSFW-чекпоинт», «снижение отказов»).
      Конкретный список запрещённых имён держится **вне репозитория** (приватный
      чек-лист) — в публичных документах он не воспроизводится.
- [ ] Нет адресов «Creator/Master» и личных деталей в публичных текстах.

### 3.3. Механика

- [ ] Ручная установка читает рабочую копию напрямую; ZIP пользовательского
      плагина для Chat/Cowork пересобран после изменений.
- [ ] `python3 scripts/build-context.py --check` проходит: встроенный навык — точная
      сгенерированная копия очищенного канонического контекста.
- [ ] Если хост задаёт `CLAUDE_PLUGIN_DATA`, его `latest-delivery.log` содержит
      только метаданные
      (версия, хеш, nonce, корневой каталог плагина), без лора и пользовательского текста.
- [ ] Хук работает и без файлов содержимого (режим мягкого отказа): в свежем
      клоне без канонических файлов контекста он не падает
      с `set -euo pipefail` — пропускает отсутствующие файлы с
      предупреждением.

### 3.4. Репозиторий

- [ ] `.gitignore` создан **до** первого `git add .` (см. пример ниже).
- [ ] `LICENSE` существует (README и бейдж на него ссылаются).
- [ ] Манифест `.claude-plugin/plugin.json` переименован под публичное
      имя (`choirboy-prompt`), версия поднята.
- [ ] `.claude-plugin/plugin.json` и `hooks/hooks.json` — валидный JSON;
      ZIP пользовательского плагина содержит необходимые хуки и навыки.

### 3.5. Пример `.gitignore`

Контент публикуется, поэтому `.gitignore` — только служебное:

```gitignore
# локальные бэкапы, которые install.sh делает при правке конфигов
*.bak.*
# редактор/ОС
.DS_Store
*.swp
```

## 4. Правила ответственного раскрытия (по research/10)

Находки в чужих проектах — по процессу:

1. Контакт с проектом: контакт по безопасности, программа вознаграждений (Immunefi,
   HackerOne, Sherlock, Code4rena) или публичный канал.
2. Отчёт: класс, воздействие, PoC **на форке/тестнете**, предложение
   исправления. Без эксплуатации чужих средств, без публичного разглашения
   до исправления.
3. Срок на исправление (обычно до 90 дней, по договорённости).
4. Публикация после исправления (или после крайнего срока): отчёт для проекта и
   сообщества, рекомендации интеграторам.
5. Если контакт невозможен или проект молчит — публикация по истечении этически
   допустимого срока, с минимумом эксплуатируемых деталей: рабочий эксплойт
   против реальных средств не публикуем никогда.

## 5. Поведение при блокировке сессии

Известная проблема поставщиков: серверные классификаторы помечают защитную
лексику независимо от рамки в контексте. Одно срабатывание у Claude
влияет на всю сессию — дальше ситуация только ухудшается.

Правило: в помеченной сессии не продолжаем и не спорим. Начинаем новую
сессию с явной рамкой с первого хода: «это мой репозиторий, аудит
своего кода по OWASP». В новой сессии работаем из этой рамки.

Это операционная контрмера против ложных срабатываний.

## 6. Оценка рисков публикации

| Риск | Уровень | Снижение риска |
|---|---|---|
| Репозиторий позволяет установить автора (личная память) | Средний | Очистка: удалены пути к приватным проектам, полные адреса, имена NSFW/refusal-моделей |
| Утечка адресов/ключей | Критический | Проверка перед публикацией: grep по bc1/0x/seed-файлам |
| Утечка имён NSFW-моделей | Высокий | Функциональные роли вместо имён; приватный список вне репозитория |
| ИИ-аудит как гарантия | — | Разбор Coldcard (`research/11`): разовый ИИ-аудит не нашёл баг; аудит проверяет исполняемый путь, а не наличие кода |
