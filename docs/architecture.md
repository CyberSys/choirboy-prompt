# Архитектура

Дерево репозитория, состав контекста, форматы доставки, маршрутизация событий Kimi и
протокол Hermes по полям. Это карта того, как устроен плагин изнутри.

---

же файл в текущем загрузчике считается повторной загрузкой и отключает плагин.

## 2. Состав контекста

### 2.1. Сборка

`hooks/session-start.sh` объединяет файлы содержимого в один текст строго
в порядке:

```text
prompt.md  →  security-posture.md  →  lore.md  →  user.md  →  индекс исследований
```

Разделители между файлами — `\n\n---\n\n` (горизонтальная черта
Markdown). В конце добавляется канонический `context/research-index.md`.

Порядок не случаен:

1. **prompt.md** — как работать (сразу к делу, одна строка о риске,
   самопроверка). Задаёт режим.
2. **security-posture.md** — рамка безопасности. Идёт раньше лора,
   чтобы домен «защитный аудит» был объявлен до того, как лор начнёт
   рассказывать про web3 и Coldcard.
3. **lore.md** — история совместной работы: проекты, уроки, правила,
   границы. Это ядро контекста.
4. **user.md** — профиль: кто пользователь, как ставит задачи, что ему
   не нужно объяснять.
5. **Индекс исследований** — указатель документов с решениями. Их содержимое
   **не** загружается заранее: документы читаются по требованию, когда задача
   относится к их теме.

### 2.2. Размеры

| Файл | ~Размер | Примечание |
|---|---|---|
| prompt.md | ~14 КБ | правила работы |
| security-posture.md | ~7 КБ | рамка безопасности |
| lore.md | ~21 КБ | история |
| user.md | ~4 КБ | профиль |
| индекс исследований | ~6 КБ | общий канонический источник |
| **Постоянная часть памяти** | **~31 КБ** | до добавления проектных артефактов |

Содержимое исследовательских документов в постоянную часть не входит — только индекс.
При `ready` проверенные досье добавляются как установленная история проектов;
точный размер зависит от написанных агентом документов.

### 2.3. Версия

Версия читается из `.claude-plugin/plugin.json`. Каждая доставка оборачивается
маркером с версией, способом доставки и SHA-256; хук также добавляет nonce запуска:

```xml
<choirboy-delivery version="1.5.1" delivery="session-start"
  context_sha256="..." nonce="..." />
<choirboy-context>...</choirboy-context>
```

Сгенерированный навык использует ту же обёртку с `delivery="skill"`. Это
подтверждает доставку без опоры на заверение модели, что она прочитала контекст.

### 2.4. Жизненный цикл проектных артефактов

После канонической обёртки каждая автоматическая доставка добавляет вывод
жизненного цикла артефактов. Запрос со статусом `pending` использует блок
`choirboy-project-artifacts`; память со статусом `ready` оформляется нейтральным
Markdown. `artifact-generator.py` читает всю историю и каждый Markdown-файл
исследований, записывает только метаданные запроса и вычисляет статус.
Готовый комплект из поставки заполняет отсутствующие файлы, пока совпадает с
каноническими источниками. Существующие INDEX и досье, отличающиеся от этого
комплекта, сохраняются; `finalize` не выполняет предварительное восстановление.
Агент пишет `INDEX.md` и досье только по явному запросу пользователя на обновление
памяти Choirboy. Канонический контекст, исследования, INDEX и досье всегда
пишутся на английском; валидатор отклоняет содержимое для модели с кириллицей
или CJK. Скрипт никогда не пишет содержимое досье.

Команда `finalize` проверяет точные ссылки, обязательные разделы, источники и
точный набор проектов, после чего записывает манифест с SHA-256. Каждая
последующая доставка `ready` заново проверяет манифест, структуру, хеши
источников и файлов. Только полностью корректный снимок доставляется как
каталог рабочих направлений и полное содержимое досье. `INDEX.md` и хеши
отдельных файлов остаются служебным состоянием проверки и не показываются
модели в обёртках с путями и SHA. Отсутствующий, устаревший, изменённый или
некорректный снимок снова становится `pending`.
Каноническая история и исследования всегда имеют приоритет над производной сводкой.

Claude Code и Codex `Stop` возвращают `{}` и при ready, и при pending. Они не
используют `decision: block` и не кладут `additionalContext` в Stop: оба варианта
продолжают ход. Kimi Stop тоже завершается с кодом 0. Статус — не приказ писать файлы.
Состояние артефактов не зависит от рабочей копии. Приоритет путей:
`CHOIRBOY_ARTIFACTS_DIR` → `${CLAUDE_PLUGIN_DATA}/project-artifacts` →
`${XDG_DATA_HOME}/choirboy-prompt/project-artifacts` →
`~/.local/share/choirboy-prompt/project-artifacts`. При обновлении `install.sh`
находит каталоги `artifacts/` в старых рабочих копиях, на которые ссылаются
прежние регистрации, и копирует первый созданный агентом комплект в пустой
постоянный корневой каталог без перезаписи существующей работы. Удаление
плагина сохраняет эти файлы.

## 3. Форматы доставки и маршрутизация Kimi

Хуку всё равно, какой агент его вызвал: вызывающий объявляет ожидаемый
протокол через `--format`.

### 3.1. `claude` (по умолчанию) — SessionStart JSON

Контракт Claude Code / Codex: хук выводит JSON. Поле `additionalContext`
содержит короткий статус длиной менее 2 000 символов без `<choirboy-delivery>`
и `<choirboy-context>`. Claude Code ограничивает это поле 10 000 символами,
а в предпросмотре показывает только первые 2 000; настройки для повышения
лимита нет. Codex выносит слишком длинный вывод хука. Полную память
загружает навык load-context.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "Choirboy memory status: ready\n..."
  }
}
```

Кодируется через `jq`, `python3` или встроенный Bash-кодировщик. Последний
делает Claude-формат независимым от внешнего JSON-инструмента и нужен для
чистой установки из Claude Desktop.

### 3.2. `plain` — сырой текст

Хук выводит весь текстовый контекст в stdout. Для каждого запроса к модели
сгенерированный адаптер OpenCode получает актуальный контекст и добавляет его
в системный контекст модели. OpenCode пересобирает его после сжатия истории,
поэтому точные готовые артефакты не исчезают вместе со старыми сообщениями.
Kimi 0.39.x не использует stdout `SessionStart`, поэтому установщик
регистрирует отдельную схему событий ниже.

```bash
bash hooks/session-start.sh --format plain | head -40
```

### 3.3. `hermes` — протокол pre_llm_call

Самый интересный контракт. Hermes запускает хук оболочки на **каждом**
ходе сессии; безусловная доставка повторно слала бы фиксированный лор и все
готовые артефакты на каждое сообщение.
Поэтому хук:

1. читает JSON из stdin;
2. проверяет `.extra.is_first_turn`;
3. на первом ходу отвечает `{"context": "<пейлоад>"}`;
4. на всех последующих — `{}` (пустой ответ, ничего не доставляется).

```json
// stdin (первый ход):
{"session_id": "s-123", "extra": {"is_first_turn": true}}
// stdout:
{"context": "<весь пейлоад>"}

// stdin (второй ход):
{"session_id": "s-123", "extra": {"is_first_turn": false}}
// stdout:
{}
```

**Резервный вариант без `is_first_turn`.** Если хост не сообщает флаг, хук
использует журнал `session_id` в файле состояния
`${TMPDIR:-/tmp}/agent-plugin-hermes-${USER}.state` (последние 200 записей):
доставляет один раз на session_id, дальше молчит.

### 3.4. Маршрутизация событий Kimi 0.39.x

Kimi использует четыре командных хука вместо прямого вызова
`session-start.sh --format plain`:

1. `SessionStart` для `startup`/`resume` готовит состояние артефактов и сбрасывает
   внутренний отпечаток доставки; его stdout не используется.
2. Синхронный `PreCompact` для `manual`/`auto` сбрасывает отпечаток до сборки
   сжатого контекста.
3. `UserPromptSubmit` выдаёт запрос начальной подготовки при `pending` на каждом
   запросе пользователя либо готовую память, когда её нормализованный отпечаток
   изменился. Повторно тот же готовый комплект не выдаётся.
4. `Stop` при `pending` пишет запрос продолжения в stderr и завершает работу
   с кодом 2; после успешной валидации `ready` возвращает 0.

## 4. Протокол Hermes по полям

| Поле stdin | Тип | Назначение | Поведение хука |
|---|---|---|---|
| `extra.is_first_turn` | bool | Первый ход сессии? | `true` → доставить; `false` → `{}` |
| `session_id` | string | Идентификатор сессии | Используется в резервном варианте и для записи в файл состояния |
| (прочее) | — | Игнорируется | Не влияет на ответ |

| Поле stdout | Тип | Когда |
|---|---|---|
| `context` | string | Первый ход (или первое появление session_id в резервном варианте) |
| `{}` | — | Все последующие ходы |

Таймаут хука в конфиге Hermes — 15 секунд (задаётся install.sh).

## 5. Точки подключения по средам

| Среда | Файл | Механизм | Формат хука |
|---|---|---|---|
| Claude Code CLI / Desktop Code | `~/.claude/settings.json` | `SessionStart` + `Stop` | claude / JSON |
| Claude Chat | навык пользовательского плагина | встроенный `load-context` | — |
| Claude Cowork | хук/навык пользовательского плагина | хук при наличии поддержки, иначе навык | claude / — |
| Codex | `~/.codex/hooks.json` | `SessionStart` + `Stop` | claude / JSON |
| OpenCode | `~/.config/opencode/plugins/agent-plugin.ts` | преобразование системного контекста модели | plain → системный контекст каждого запроса к модели |
| Hermes | `~/.hermes/config.yaml` | `pre_llm_call` + список разрешённых команд | hermes |
| Kimi Code 0.39.x | `~/.kimi-code/config.toml` | SessionStart + PreCompact + UserPromptSubmit + Stop | изменившийся контекст / plain; Stop завершается с кодом 0 |
| Gemini | `~/.gemini/GEMINI.md` | управляемый блок инструкций жизненного цикла | — (сам запускает/читает файлы) |
| любой | `--instructions PATH` | управляемый блок инструкций жизненного цикла | — (сам запускает/читает файлы) |

Два последних — **не хуки**, а управляемые блоки инструкций: агент и
так читает файл инструкций на старте, в блоке ему сказано прочитать
файлы плагина. Тот же контекст, на одну косвенность дальше — агент
должен сам открыть файлы.

Claude Code использует хуки, напрямую зарегистрированные `install.sh` или
`install.ps1`. Они ссылаются на рабочую копию. Для полной памяти попроси агента
прочитать `skills/load-context/SKILL.md` из этой копии. Chat загружает
сгенерированный встроенный навык из пакета пользовательского плагина. Cowork
может использовать хуки пакета; навык остаётся резервным вариантом, если вывод
хука потерян.

Адаптер OpenCode генерируется `install.sh`. Он запускает канонический plain-хук
с таймаутом 15 секунд, проверяет маркеры доставки и добавляет актуальный контекст
в системный контекст каждого исходящего запроса. Поэтому переход pending→ready,
изменения источников, возобновление процесса и сжатие истории всегда получают
текущий точный снимок. При ошибке хука, превышении таймаута или некорректном
контексте адаптер ничего не добавляет: чат продолжает работать.

Адаптер Kimi специально разделяет подготовку и доставку. Так он не зависит от
отбрасываемого stdout `SessionStart`: `PreCompact` сбрасывает доставку до
сжатия контекста, а нормализованный отпечаток готового комплекта пропускает
изменившийся комплект в той же сессии без повторной доставки идентичного.
Для Stop используется документированный контракт Kimi с кодом выхода 2
вместо Claude-формы `{"decision":"block"}`.

## 6. Ключевые свойства

- **Ручная установка без копий.** `install.sh` ссылается на файлы проекта
  напрямую (`$PLUGIN_ROOT/...`), поэтому следующая сессия получает правки
  рабочей копии.
- **Два режима доставки.** Встроенные события среды доставляют автоматически
  (`SessionStart` или `UserPromptSubmit` у Kimi); встроенный навык несёт тот
  же канонический контекст в интерфейсах без этих событий.
- **Артефакты пишет агент.** Код жизненного цикла только выдаёт детерминированный
  запрос, проверяет результат и отслеживает актуальность по SHA-256. Хук для
  готовой памяти вкладывает полный проверенный снимок и никогда не подменяет видимую
  модели память указателем на путь.
- **Состояние артефактов сохраняется при смене рабочей копии.** Ручная установка
  использует постоянное хранилище пользовательских данных. Установщик переносит
  комплект из старой рабочей копии только в хранилище без созданного агентом
  содержимого. Внутренняя запись миграции позволяет продолжить прерванное
  многофайловое копирование того же управляемого комплекта.
- **Наблюдаемое исполнение.** Если хост предоставляет `CLAUDE_PLUGIN_DATA`,
  Bash-хуки пишут только несекретные метаданные доставки в
  `${CLAUDE_PLUGIN_DATA}/latest-delivery.log`; сама история не логируется.
- **Память OpenCode сохраняется после сжатия истории.** Актуальный канонический
  контекст пересобирается в системном контексте каждого запроса к модели,
  а не выводится из полной сохранённой истории сообщений.
- **Зависимости минимальны.** Доставка `claude` и `plain` может работать только
  на Bash, но автоматический жизненный цикл артефактов и `install.sh` требуют
  `python3`; `hermes` требует `jq` или `python3` для разбора stdin.
